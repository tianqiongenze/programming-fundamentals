### 知识四要素详解（V1.2深度版·与授课PPT同源）

**B01 Modbus寄存器**
- 定义：寄存器=PLC的储物柜编号：40001起按地址读数
- 使用场景：五测点(温度/压力/振动/转速/状态)固定地址——通信的门牌号
- 应用实例：client.read_holding_registers(address=0, count=5)
- 扩展与误区：误区：地址从0还是40001起两派之争——以server文档为准
- 原理：Modbus寄存器是16位整数仓库：PLC的每个寄存器有地址(40001起)，读写按地址存取——工控领域最通用协议
- 判断依据：虚拟设备模拟：pymodbus开服务端把温度'放'进寄存器，客户端按地址读——现场PLC同构
- 逐行解释：from pymodbus.server import StartTcpServer 模拟器；context块里定义寄存器表——HoldingRegister 40001存温度785（见B02）
- 进阶优化：功能码03读保持寄存器/06写单寄存器是两大常用码；进阶ModbusTcpClient批量read_registers一次拉一段

**B02 定点存储约定**
- 定义：定点=小数×10存整数：678其实是67.8℃——PLC不存小数
- 使用场景：行业惯例：约定小数位，通信只传整数
- 应用实例：raw=678 → real=raw/10 → 67.8℃
- 扩展与误区：误区：忘除倍率→温度高10倍——对不上先查约定倍率
- 原理：寄存器只认16位整数——78.5℃要拆成785（放大10倍存），读回再÷10还原：定点数约定=双方说好的放大倍数
- 判断依据：温度/压力带小数都要定点化：写端×10存、读端÷10还原——约定写进数据字典，两端一致才不乱
- 逐行解释：写：int(temp*10)→785存寄存器；读：raw/10→78.5还原——放大倍数10是两端合同；负温用补码（进阶了解）
- 进阶优化：小数位多就×100（精度0.01）；进阶32位浮点拆两个寄存器(高16低16)组合——高精度传感常用此法

**B03 pymodbus读寄存器**
- 定义：pymodbus=Python的Modbus翻译官——一行读PLC寄存器
- 使用场景：Modbus TCP读PLC保持寄存器——采集主链路
- 应用实例：rr = client.read_holding_registers(0,5)
- 扩展与误区：误区：3.x必须关键字传参(address=/count=)——照2.x旧码抄报错
- 原理：pymodbus客户端三步：连IP端口→read_holding_registers(地址,数量)→取.value——像查仓库货架
- 判断依据：边缘网关轮询采集：每5秒读一次3号泵温度寄存器——连接复用别每轮重连（握手开销大）
- 逐行解释：client=ModbusTcpClient('127.0.0.1',502) 连；rr=client.read_holding_registers(0,1) 读0号起1个；rr.registers[0] 取值——三行完成一次采集
- 进阶优化：超时参数timeout=2防卡死；连接断了走重连逻辑（try+close+connect）；进阶异步客户端AsyncModbusTcpClient高并发

**B04 MQTT主题路由**
- 定义：MQTT=广播电台：主题=频道，发布订阅各取所需
- 使用场景：一个采集器发布，多个监控端订阅——一对多广播
- 应用实例：publish('device/1/status', json_msg)
- 扩展与误区：误区：主题乱起名难管理——层级命名device/1/status是惯例
- 原理：MQTT是发布/订阅模型：设备只管往主题发(publish)，谁关心谁订阅(subscribe)——发送方与接收方互不认识，靠broker中转
- 判断依据：多设备上报一个平台、平台分组下发：主题按'工厂/车间/设备/属性'分层命名——topic即路由表
- 逐行解释：publish('ljsz/plant1/pump3/temp','78.5') 发布；subscribe('ljsz/plant1/+/temp') 通配符订阅全车间温度——+单层、#多层
- 进阶优化：QoS 0最多一次/1至少一次/2恰好一次——告警用QoS1防丢；retain=True保留最后一条，新订阅者秒拿最新值

**B05 JSON消息含时间戳**
- 定义：ts时间戳=消息的出生证明——排序追溯全靠它
- 使用场景：监控端按时间画曲线/排查先后顺序
- 应用实例：msg={'id':'DEV-1','ts':time.time(),…}
- 扩展与误区：误区：靠接收时间排序——网络延迟会歪曲时序，ts放消息体
- 原理：JSON消息带时间戳=数据自带'出生证明'：{dev_id,temp,ts}三元组——没有ts的数据无法回溯与对账
- 判断依据：一切上报消息必带ts（毫秒时间戳）——离线补传时按ts排序还原真实时序
- 逐行解释：msg={'dev':'P3','temp':78.5,'ts':int(time.time()*1000)} 组消息；json.dumps后publish——消费端按ts去重+排序
- 进阶优化：时间戳统一毫秒int（跨系统对齐）；进阶ISO8601字符串带时区（'2026-09-28T08:00:00+08:00'）人类可读

**B06 排错三步法**
- 定义：排错三步=从外到内剥洋葱：ping通→端口通→代码通
- 使用场景：网络采集故障的分层排查——每层排除再进下一层
- 应用实例：ping 192.168.x.x → 测502端口 → 查pymodbus报错
- 扩展与误区：误区：一上来改代码——先ping再说，80%是网络层的事
- 原理：排错三步法=先物理(ping通吗)→再协议(端口/地址对吗)→后数据(格式/值对吗)——从底层往上排，别上来就改代码
- 判断依据：采不上数的标准排查序：网线/IP→502端口/寄存器地址→定点倍数/编码——九成故障停在前两层
- 逐行解释：ping 192.168.1.10 不通查网线；telnet ip 502 拒绝查服务；读到32767明显是定点倍数错——分层定位三分钟见分晓
- 进阶优化：抓包Wireshark过滤modbus/mqtt看真实字节流——终极武器；日志埋点记录每轮采集成败率做趋势监控

## 避坑
- pymodbus 3.x返回值是对象 → `rr.registers` 取数；
- MQTT publish后立刻退出 → 循环结束加 `client.loop_stop()` 与短暂sleep；
- 寄存器是×10定点 → 温度读数678实为67.8℃。
